# XIV DB：Tera 2 全量构建耗时剖析

日期：2026-10-31。对象：51,225 物品详情、513 目录、1 首页，共 51,739 张 HTML。

## 结论

当前不是 Tera 模板执行占主导。纯 Tera 渲染约 **0.247 s / 4.0%**；更值得先处理的是：

1. 每页重复创建和校验内置 HTML registry；目前 registry 装配与 Renderer 初始化所在区间合计约 0.79 s。
2. 整站数据先构造 serde_json::Value，再转 Tera Value，共享上下文区间约 0.695 s，另有目录数据构建约 0.088 s。
3. prepare 扩展约 1.357 s，其中 Python 花约 0.657 s 输出 34.36 MB JSON，Rust 另花约 0.161 s 解码响应。
4. 发布约 1.047 s；写文件约 0.474 s，删除上一版输出约 0.339 s。

以上是测得的成本区间，不是已验证可以全部消除的收益；本轮只剖析，未实施优化。

## CPU 图中的证据

下列采样百分比的分母是 **Notist 进程 CPU 样本**，不是 wall time，累计占比之间可能重叠：

- libc 分配/释放相关叶子符号（malloc/free/realloc 及其内部实现）的 **flat 合计约 35.57% / 1.739 CPU s**。这是互斥叶子样本求和，没有把 malloc 的父子累计比例重复相加。说明应减少重复构造与复制，不意味着第一步就应该换 allocator。
- `std::path::compare_components` 累计约 10.98%，自身约 6.76%。路径键的有序表查找、插入和反复环境查询值得关注；不能把累计占比全算成路径比较函数本身。
- `HtmlRegistry::default` 累计约 13.16%。从源码确认：`from_bindings` 先创建默认 registry，而 `Renderer::new().with_registry(registry)` 又创建默认 registry 再立即替换。
- `HtmlRegistry::register` 每次克隆 definition 并 `validate_module`，内置函数也经过该路径。5 万级页面放大了这些重复工作。
- `Tera::render` 在 CPU 图中累计约 5.12%，与阶段计时所得约 4% wall time 方向一致。

关键源码位置（Notist 仓库）：

## 建议优化顺序（尚未实施）

1. **减少重复 HTML registry 构造。** 先给已绑定 registry 的 Renderer 提供不先生成默认 registry 的构造路径，再考虑复用已校验的内置 registry/definition。必须保持用户组件的校验、错误诊断和页面绑定语义；约 0.79 s 是目前被收费的区间，不是保证可省的时间。
2. **减少共享上下文的中间 JSON 与临时副本。** 考虑直接序列化结构到 Tera Value，并复用目录/页面数据；保留 site.pages、site.directories 和 site.data 的整站查询契约，不能靠隐藏数据变快。
3. **优化 Python JSON 响应编码。** 验证 C 加速的 json.dumps + 批量 write 能否替代 json.dump 的流式 Python 编码路径；检查峰值内存及 Unicode/协议兼容性。无需先重写 CSV 解析器或更换扩展协议。
4. **再看文件发布和路径访问。** 缓存已创建目录、减少重复 environment/path 查询；更长期考虑保持原子替换、错误保留与陈旧文件清理语义的增量发布。不能简单取消旧文件清理或安全校验。

除非站点模板复杂度改变，继续微调 Tera VM 本身的潜在整程收益受到约 4% 当前占比限制。
